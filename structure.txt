> backend to the screen. Items marked **NEW** were added with the
> "Register a person" and "Tenants" features.

## 1. Architecture in One Minute

The `features/` folder follows an **MVVM pattern**. Every feature is split the same way:

| Layer | Folder | Responsibility |
|---|---|---|
| **Model** | `models/` | Shape and normalisation of data (what a Production, Product, User looks like). Also holds validation rules (`*.schema.js`) |
| **Service** | `services/` | API calls only. No UI, no state |
| **View-Model** | `view-models/` | React hooks (`use-...-view-model.js`) holding logic, state, grouping and calculations for a screen |
| **View** | `views/` | Pure UI (`.jsx`) that renders what the view-model gives it |
| **Store** | `store/` | Global client state (auth only) |

Pages in `src/app/` stay thin: they pick a view-model and render a view or cards.

**Guards** (in `components/common/`) decide who may see a page:

| Guard | Used on | Rule |
|---|---|---|
| `AuthGuard` | Every page inside `DashboardLayout` | Logged-out users are sent to the login page |
| `GuestGuard` | The login page `/` | Logged-in users are sent to the dashboard |
| `SuperAdminGuard` **NEW** | Registration and Tenants pages (currently switched off) | Only a Super Admin sees the page |

**Shared building blocks** **NEW**

| File | Use |
|---|---|
| `components/common/modal.jsx` | One reusable popup (closes with X, background click or Escape, locks page scroll). Used by the tenant popups |
| `lib/api-error.js` | Turns any API or network error into one readable message (`error`, `message`, `detail` or plain text) |

## 4. Data Traceability: How Data Travels

Read each chain left to right. The first file is what the user sees, the last is
where the data starts.

### 4.1 Login and staying logged in

```
login-view.jsx
  -> use-login-view-model.js      (form + validation from login.schema.js)
  -> auth.service.js              (POST login endpoint from api-endpoints.js)
  -> auth.model.js                (normalises the response into user + token)
  -> auth.store.js  setAuth()     (saved in the browser: "xoomgrid-auth")
     + localStorage "token" / "user"
  -> redirect to ROUTES.DASHBOARD
```

**Every later API call:** `lib/axios/client.js` + `interceptors.js` read
`localStorage.token` and send it as `Authorization: Bearer ...`.

**Reopening the site or a closed tab**

1. `auth.store.js` reads the saved login back from the browser and sets `hasHydrated = true`.
2. `AuthGuard` (dashboard pages) or `GuestGuard` (login page) waits for `hasHydrated`.
3. Token found: dashboard pages open, and the login page jumps to the dashboard. No token: the login page shows.

**Logout:** `auth.store.js logout()` is the **only** place a saved login is removed.
It clears the store and deletes `token` and `user` from the browser, then the page
returns to `/`.

### 4.2 Live machine cards (Dashboard and TV)

```
app/dashboard/page.js  (or app/tv/page.js)
  -> use-production-view-model.js   (refreshes every 30 sec, groups the cards)
  -> production.service.js          (POST /proddata/assemblyshift, one call per machine)
  -> production.model.js            (snake_case -> camelCase, fixes the timestamps)
  -> machine cards (status, counts, cycle time, last update)
```

- **Running or stopped:** a machine is *running* if its last production event is at most
  15 minutes old, otherwise *stopped* (red). The status is re-checked every 15 seconds,
  even if no new data arrives. The timeout lives in `constants/all-constants.js`.
- **Time fix:** the device sends India time (IST) but labels it as UTC (`Z`). The model
  subtracts the 5 h 30 min offset to get the real time. When the backend sends true UTC,
  set the offset to `0`.
- **Request body:** `tenant_id`, `device_id`, and where needed `station` (RH / LH) and
  `variant` (HIGH / LOW).

### 4.3 Registering a person (NEW)

```
app/employees/create/page.js
  -> DashboardLayout (AuthGuard)  +  SuperAdminGuard (switched off for now)
  -> create-employee-view.jsx
  -> use-create-employee-view-model.js   (react-hook-form + employee.schema.js)
  -> employee.service.js                 (mock now, API later)
  -> employee.model.js  buildEmployeePayload()   (form fields -> API field names)
```

- **Dropdowns:** departments and roles load through `employee.service.js` and are cached
  for 10 minutes, so the form opens instantly after the first load.
- **Saving** is one request. The form uses react-hook-form, so typing does not re-render
  the page.
- **Success box:** after saving, the new person's temporary password is shown **once**
  (with a Copy button) and is kept only in memory.
- **Mock mode:** with `USE_MOCK = true`, nothing reaches a server. Saving answers
  instantly, and a duplicate Employee ID returns an error so the error message can be tested.

### 4.4 Hourly charts (Monitoring)

```
app/monitoring/page.js
  -> hourly-production-view.jsx
  -> use-hourly-production-view-model.js   (station / variant selection, totals, best / lowest hour)
  -> hourly-production.model.js            (shapes hourly data)
```

Bars are **green** when the hour met its target and **red** when below. The data
source must return a count **per hour**. A shift-total snapshot alone cannot be turned
into hourly bars.

### 4.5 Tenants: list, create and verify (NEW)

```
app/tenants/page.js
  -> DashboardLayout (AuthGuard)  +  SuperAdminGuard (switched off for now)
  -> tenants-view.jsx
  -> use-tenants-view-model.js         (list, search, filter, sort, verify state)
  -> tenant.service.js
  -> tenant.model.js                   (API answer -> screen shape)
```

| Action | Screen | Call | Body | Answer |
|---|---|---|---|---|
| List | `tenants-view.jsx` | `POST /tenant/list` | `{ "sort_order": "asc" \| "desc" }` | `{ sucess, message, data: [...] }` (the backend spells it `sucess`) |
| Create | `create-tenant-modal.jsx` via `use-create-tenant-view-model.js` | `POST /tenant/createtenant` | `tenant_name`, `tenant_code`, `address` | The new tenant, or `{ "error": "tenant Code already exists" }` |
| Verify | `verify-tenant-modal.jsx` via `use-tenants-view-model.js` | `POST /tenant/verifytenant` | `{ "tenant_code": "..." }` | Plain text: `Tenant Verified` or `Tenant Already Verified` |

- **Verified badge:** a verified tenant shows a green *Verified* badge. A tenant that is not
  verified shows an amber *Not verified · Verify* badge. Clicking it opens the verify popup.
- **After verifying:** the saved list is patched at once so the badge turns green, then the
  list reloads from the server to confirm.
- **After creating:** the list reloads so the new tenant appears (as not verified). The success
  popup shows the tenant **as the server saved it**, including the code the server returned.
- **Errors:** an answer such as `{ "error": "..." }` is treated as an error even with a 200
  status (`tenant.service.js`). A duplicate code shows under the *Tenant code* field.
- **Timestamps:** these come with `+05:30`, so they are shown as they are. The IST fix used
  for production data is **not** needed here.
- **Server:** all three calls use the one `BASE_URL`. The create, list and verify APIs must be
  reachable on that same server.

## 6. Access Control and Security Notes

- **Screen checks are not security.** `AuthGuard`, `GuestGuard` and `SuperAdminGuard`
  only control what the screen shows. The **backend must also check the token and the
  role** on every protected call, especially when creating a person.
- **Super Admin role name:** `constants/roles.js` lists the accepted values
  (`SUPER_ADMIN_ROLES`). They must match the `user_role` returned by the login API.
- **Token storage:** the token is kept in the browser's `localStorage`. This is fine for
  an internal app, but any script on the page could read it.
- **No token expiry:** the current token has no `exp`, so a login lasts until the user
  presses Logout. Ask the backend to add an expiry (for example 7 or 30 days).
- **Tenant verification is a powerful action.** Anyone who can open `/tenants` can verify a
  tenant. Put `SuperAdminGuard` back on that page, and make the backend allow
  `/tenant/verifytenant` and `/tenant/createtenant` only for a Super Admin.
- **Sign-out is explicit:** users are never sent to the login page except by pressing
  Logout.

## 8. How to Add a New Feature

1. Create `features/<name>/` with `models/`, `services/`, `view-models/`, `views/`.
2. **Model:** shape and validate the data. **Service:** only the API calls.
3. **View-model:** a `use-<name>-view-model.js` hook with the logic and state.
4. **View:** a `.jsx` file that only renders what the view-model returns.
5. Add a thin page in `src/app/<route>/page.js`, wrapped in `DashboardLayout`.
6. Add the API URL to `config/api-endpoints.js` and the route to `constants/routes.js`.
7. Add the new files to the tree in this document.
